# Local development, verification, and release preparation

## Configuration and local stack

The backend uses Python 3.12, `uv`, FastAPI, PostgreSQL, and Alembic. The website uses Node 22, npm, and Next.js. The checked-in `uv.lock` and `package-lock.json` are the dependency sources for containers and CI.

Run `./scripts/local-env.sh` to create an ignored `.env.local` with random local database, operator, and provider secrets. If the file predates the provider portal, the script adds only the missing provider secret. `.env.example` contains placeholders only. Do not print the generated values, pass them as build arguments, or copy them into images. For direct development, set `DATABASE_URL` to a disposable PostgreSQL psycopg URL, `ADMIN_CREDENTIALS_JSON` to a JSON object mapping operator IDs to distinct secrets of at least 32 characters, and `PROVIDER_CREDENTIALS_JSON` to provider IDs with a distinct long secret and organization key. Run `cd backend && uv sync --locked`, `uv run alembic upgrade head`, and `uv run uvicorn app.main:create_app --factory`. For the website, run `cd frontend && npm ci`, then `DIRECTORY_API_URL=http://127.0.0.1:8000 npm run dev`. `DIRECTORY_API_URL` is server only. To test submissions outside Compose, set `FEEDBACK_ENABLED=true` in both local processes. Keep `PORTAL_COOKIE_SECURE=false` only for the local HTTP preview; production must use HTTPS, set it to `true`, and set `PORTAL_ORIGIN` to the exact public origin used for CSRF validation.

For a local container run, use `./scripts/local-env.sh` followed by `docker compose --env-file .env.local -f compose.local.yaml up --build --wait`. The site binds only to `127.0.0.1:3018`; PostgreSQL and the backend have no published ports. Stop this project's containers with `docker compose --env-file .env.local -f compose.local.yaml down`. Its named volume keeps local data until deliberately removed. The Compose project is `iter-directory-local`; its networks and volume are project scoped. The database and backend share an internal network; the frontend reaches only the backend through a separate network. Runtime images use a non-root UID, read-only filesystem, reduced capabilities, bounded logs, health checks, and a restart policy. One backend worker is used because its current rate limit is process local. Run `./scripts/local-seed.sh` against the running stack to create the fictional provider organization and publish fictional listings and approved reviews through the operator API. Every fixture employer is marked `(fictional)` and uses reserved `example` domains. A rerun does nothing while the full set is current; otherwise it closes leftover fixture listings and publishes a fresh set for the next season. Local Compose sets `DIRECTORY_DEMO_MODE=true`, so its pages are always labelled as demonstration data. Use the generated `ITER_PROVIDER_TOKEN` at `/portal/login` for the provider workspace or `ITER_ADMIN_TOKEN` for the operator console; never paste either value into source, logs, screenshots, or chat.

Same-origin `/api/feedback/reviews` and `/api/feedback/reports` forward bounded JSON to the backend. Both services require `FEEDBACK_ENABLED=true` before accepting submissions; otherwise forms are hidden and writes return 503. Local Compose enables it for testing. Changing the setting requires restarting both services. Do not enable it for public traffic until an operator-approved HTTPS ingress, shared client-aware rate limit, confirmed data location, and personal-data plan are in place. Set `TELEGRAM_BOT_USERNAME` and optional `TELEGRAM_APP_SHORT_NAME` only when the Mini App points at this site. Without them, its launch link stays hidden. Direct links use `startapp=job_<listing UUID>` and resolve `tgWebAppStartParam` to the normal detail route. `DIRECTORY_DEMO_MODE=true` visibly labels fictional fixture data and must not be enabled publicly. No Telegram bot token belongs in the website bundle. Keep development, test, and production databases separate; never use real student data in fixtures, screenshots, logs, or CI artifacts.

## Verification and CI

Run `./scripts/verify.sh` from the repository root. It scans source and Git history for secrets, runs ShellCheck on `scripts/`, validates Compose, builds the backend and frontend images, migrates an empty disposable database and checks Alembic's head, runs Ruff and backend tests against PostgreSQL, rehearses a database dump and restore, audits locked Python dependencies, starts the local stack, checks its health, and seeds it twice to confirm fixtures publish and reruns are no-ops, then runs locked npm installation, formatting, type checks, unit/component tests, a production build, Playwright smoke tests, and an npm vulnerability audit. The script uses the separate `iter-directory-check` Compose project and localhost port 3019, then removes only its disposable containers and volumes. It does not remove the normal local volume. CI runs this same script on pull requests, pushes to `main`, and a weekly schedule that catches newly published advisories, with read-only repository permission and pinned action commits. A newer push cancels an older run only on pull requests, so every `main` commit keeps its result. Dependabot opens weekly minor and patch update pull requests for npm, uv, GitHub Actions, Dockerfile, and Compose image pins; review and merge them like any other change. Major updates are ignored because Python 3.12, Node 22, and PostgreSQL 17 are deliberate pins; a PostgreSQL major upgrade also needs a dump and restore of existing data. Plan major upgrades as separate tasks.
Set `PLAYWRIGHT_PORT` to a free local port when running Playwright while the normal Compose frontend is using 3018.

The regression floor is behavioral: backend API/auth/lifecycle tests, frontend component tests, and browser flows for browsing, detail, filters, stale status, direct-contact safety, and narrow viewport. There is no percentage coverage gate. Playwright uses fictional local data. A real Telegram client launch, TLS ingress, and production rate limits remain unverified.

## Backup, migration, and rollback

Use additive, backward-compatible migrations and test upgrades from the prior schema with representative data. The local verification script upgrades an empty database and restores a dump into another disposable database, comparing table row counts. This is a local rehearsal, not evidence that a production backup is restorable. Store production backups encrypted in an access-controlled, approved location with a documented retention period. Rehearse restoration in staging before the first release and after database changes. A restore should create a separate database first, run `pg_restore --exit-on-error`, validate schema and row counts, and only then replace a failed deployment's database.

Any future deployment must stop if preflight, backup, migration, or health checks fail. Test rollback in staging using the previous image and a pre-migration backup. Do not assume Alembic downgrade is safe: an existing downgrade drops report and review columns. Give the running API a database role limited to its required data operations; keep schema migration privileges in a separate role and set connection and query timeouts against the host's capacity. Production routing and deploy scripts are deferred until the host has been inspected through an approved, key-based, read-only account.

## Human steps before deployment can be enabled

The operator reports that the previously exposed VPS credential has been rotated and the old access disabled; this has not been independently verified. Use a dedicated non-root deployment account with a scoped SSH key and pinned host key. Inspect the VPS architecture read-only: Wished/Clavis and shared Caddy ownership, existing port bindings, Compose projects, networks, volumes, backups, and host/data location. The operator reports that the proposed Hetzner VPS is in Helsinki, Finland. [Article 12 of Kazakhstan's personal-data law](https://old.adilet.zan.kz/eng/docs/Z1300000094) requires personal data to be stored in a database in Kazakhstan. Obtain qualified review of whether review/report text and operational records are personal data under this rule, then choose compliant storage and a backup destination before enabling public feedback. A production design must preserve the shared proxy and unrelated projects, reserve unique Compose names, and keep PostgreSQL private; it must not bind ports 80 or 443 or restart other containers.

`main` requires a pull-request review, a passing `verify` check, and resolved conversations, but repository admins may bypass these and push directly; a direct push skips review and CI gating, so run `./scripts/verify.sh` before pushing. Restore admin enforcement before enabling deployment from `main`. A human must configure a GitHub `production` environment restricted to the protected branch with required reviewers. After approving the host plan, add its scoped SSH key, pinned host key, host identity, and runtime secrets as environment secrets. A future manual deployment workflow must name that environment and block on the preflight, backup, migration, and health gates above. This repository currently has no production workflow, routing configuration, production secrets, or production host access.
