# Local development, verification, and release preparation

## Configuration and local stack

The backend uses Python 3.12, `uv`, FastAPI, PostgreSQL, and Alembic. The website uses Node 22, npm, and Next.js. The checked-in `uv.lock` and `package-lock.json` are the dependency sources for containers and CI.

Run `./scripts/local-env.sh` to create an ignored `.env.local` with a random local database password, operator bearer secret, and a random local stand-in for the Telegram bot token. If the file predates Telegram sign-in, the script adds only the missing stand-in token. `.env.example` contains placeholders only. Do not print generated values, pass them as build arguments, or copy them into images. For direct development, set `DATABASE_URL` to a disposable PostgreSQL psycopg URL, `ADMIN_CREDENTIALS_JSON` to a JSON object mapping operator IDs to distinct secrets of at least 32 characters, `TELEGRAM_BOT_TOKEN` to a BotFather-shaped token, and `OPERATOR_TELEGRAM_IDS` to comma-separated numeric Telegram user IDs. Run `cd backend && uv sync --locked`, `uv run alembic upgrade head`, and `uv run uvicorn app.main:create_app --factory`. For the website, run `cd frontend && npm ci`, then `DIRECTORY_API_URL=http://127.0.0.1:8000 npm run dev`. `DIRECTORY_API_URL` is server only. To test submissions outside Compose, set `FEEDBACK_ENABLED=true` in both local processes. Set `PORTAL_ORIGIN` to the exact public origin and `PORTAL_COOKIE_SECURE=true` behind production HTTPS; local Compose deliberately leaves secure cookies off for `http://127.0.0.1`.

For a local container run, use `./scripts/local-env.sh` followed by `docker compose --env-file .env.local -f compose.local.yaml up --build --wait`. The site binds only to `127.0.0.1:3018`; PostgreSQL and the backend have no published ports. Stop this project's containers with `docker compose --env-file .env.local -f compose.local.yaml down`. Its named volume keeps local data until deliberately removed. The Compose project is `iter-directory-local`; its networks and volume are project scoped. The database and backend share an internal network; the frontend reaches only the backend through a separate network. Runtime images use a non-root UID, read-only filesystem, reduced capabilities, bounded logs, health checks, and a restart policy. One backend worker is used because its current rate limit is process local. Run `./scripts/local-seed.sh` against the running stack to create the fictional company profile and publish fictional listings and approved reviews through the operator API. Local Compose makes Telegram ID 1000001 an operator. Every fixture employer is marked `(fictional)` and uses reserved `example` domains. A rerun does nothing while the full set is current; otherwise it closes leftover fixture listings and publishes a fresh set for the next season. Local Compose sets `DIRECTORY_DEMO_MODE=true`, so its pages are always labelled as demonstration data. Use `./scripts/local-portal-link.py operator` to open the local operator console. Create a company in that console, copy its one-time key, and sign in at `/portal/login` to test the provider flow without Telegram. The local operator launch cannot authenticate against a real deployment. Never paste access keys or `.env.local` values into source, logs, screenshots, or chat.

Same-origin `/api/feedback/reviews` and `/api/feedback/reports` forward bounded JSON to the backend. Both services require `FEEDBACK_ENABLED=true` before accepting submissions; otherwise forms are hidden and writes return 503. Local Compose enables it for testing. Changing the setting requires restarting both services. Production Caddy overwrites `X-Iter-Client-IP` from the connection address before the frontend forwards it over the private application network; do not expose the backend or enable that trust setting outside this topology. Do not enable feedback for public traffic until an operator-approved HTTPS ingress, a shared limiter for any multi-process deployment, confirmed data location, and a personal-data plan are in place. Set `TELEGRAM_BOT_USERNAME` and optional `TELEGRAM_APP_SHORT_NAME` (only for a Mini App created with `/newapp`; leave it empty for the bot's main Mini App) only when the Mini App points at this site. Without them, its launch link stays hidden. Direct links use `startapp=job_<listing UUID>`, `startapp=manage`, or `startapp=admin` and resolve `tgWebAppStartParam` to the matching route. `DIRECTORY_DEMO_MODE=true` visibly labels fictional fixture data and must not be enabled publicly. The bot token belongs only in the backend environment, never in the website bundle or its environment. Keep development, test, and production databases separate; never use real student data in fixtures, screenshots, logs, or CI artifacts.

## Verification and CI

Run `./scripts/verify.sh` from the repository root. It scans source and Git history for secrets, runs ShellCheck on `scripts/`, validates Compose, builds the backend and frontend images, migrates an empty disposable database and checks Alembic's head, runs Ruff and backend tests against PostgreSQL, rehearses a database dump and restore, audits locked Python dependencies, starts the local stack, checks its health, and seeds it twice to confirm fixtures publish and reruns are no-ops, then runs locked npm installation, formatting, type checks, unit/component tests, a production build, Playwright smoke tests, and an npm vulnerability audit. The script uses a disposable Compose project and localhost port 3019, then removes only its disposable containers and volumes. It does not remove the normal local volume. CI runs the same script in separate `security`, `backend`, `frontend`, and `browser` scopes. A path filter selects backend, frontend, and browser scopes from changed files; workflow, script, deployment, and scheduled changes select all relevant scopes. The security scan always runs, and a final `verify` job remains the required branch and deployment gate while accepting skipped scopes only when the path filter did not select them. These jobs run on pull requests, pushes to `main`, and a weekly schedule that catches newly published advisories, with read-only repository permission and pinned action commits. A newer push cancels an older run only on pull requests, so every `main` commit keeps its result. When the repository variable `DOCKERHUB_USERNAME` and secret `DOCKERHUB_TOKEN` (a read-only Docker Hub access token) are set, the security, backend, and browser jobs sign in to Docker Hub before pulling images, which avoids the anonymous pull limit on shared runners. Pull requests from forks and repositories without these settings pull anonymously. Those jobs also point the runner's Docker daemon at the `mirror.gcr.io` Docker Hub mirror; images are pinned by digest, so the mirror can only serve identical content, and anything it lacks is pulled from Docker Hub. A failed Docker Hub sign-in does not fail the job on its own. Dependabot opens weekly minor and patch update pull requests for npm, uv, GitHub Actions, Dockerfile, and Compose image pins; review and merge them like any other change. Major updates are ignored because Python 3.12, Node 22, and PostgreSQL 17 are deliberate pins; a PostgreSQL major upgrade also needs a dump and restore of existing data. Plan major upgrades as separate tasks.
Set `PLAYWRIGHT_PORT` to a free local port when running Playwright while the normal Compose frontend is using 3018.

The regression floor is behavioral: backend API/auth/lifecycle tests, frontend component tests, and browser flows for browsing, detail, filters, stale status, direct-contact safety, and narrow viewport. There is no percentage coverage gate. Playwright uses fictional local data. A real Telegram client launch, TLS ingress, and production rate limits remain unverified.

## Backup, migration, and rollback

Use additive, backward-compatible migrations and test upgrades from the prior schema with representative data. The local verification script upgrades an empty database and restores a dump into another disposable database, comparing table row counts. This is a local rehearsal, not evidence that a production backup is restorable. Store production backups encrypted in an access-controlled, approved location with a documented retention period. Rehearse restoration in staging before the first release and after database changes. A restore should create a separate database first, run `pg_restore --exit-on-error`, validate schema and row counts, and only then replace a failed deployment's database.

Any future deployment must stop if preflight, backup, migration, or health checks fail. Test rollback in staging using the previous image and a pre-migration backup. Do not assume Alembic downgrade is safe: an existing downgrade drops report and review columns. Give the running API a database role limited to its required data operations; keep schema migration privileges in a separate role and set connection and query timeouts against the host's capacity. The production stack still uses one database role for migrations and the API; splitting them remains open.

## Production on the shared host

The host at `204.168.170.66` (Ubuntu 24.04, x86_64, 3.7 GiB RAM shared with about thirty containers, Helsinki) runs one Caddy, `wished-caddy`, which owns ports 80 and 443 and reads `/home/deploy/wished/infra/caddy/Caddyfile.production` from the Wished repository. Every project joins the shared `wished_wished-app` network for ingress, deploys from a checkout under `/home/deploy/<project>` as the non-root `deploy` user, and writes daily backups to `/var/backups/<project>`. `iter.anxchywl.dev` already resolves to the host.

`compose.production.yaml` follows that pattern under the Compose project `iter`. Every container is named (`iter-postgres`, `iter-migrate`, `iter-api`, `iter-web`, `iter-backup`) because a bare service name on the shared network is resolved round-robin across projects. Only `iter-web` joins `wished_wished-app`; the API and PostgreSQL share internal networks and publish no ports, so the operator bearer API is reachable only from the host. Containers have memory limits (about 770 MiB in total, about 140 MiB measured at idle), read-only filesystems, dropped capabilities, and bounded logs. `iter-backup` writes a custom-format dump daily and keeps `BACKUP_KEEP` of them; those dumps stay on the same disk until an off-host copy is arranged.

`deploy/Caddyfile.iter` is the site block to append to the shared Caddyfile. It sets no `X-Frame-Options`, because Telegram Web embeds the public and operator Mini App pages and route-specific CSP keeps company login and management pages same-origin only. It sets no access log because launch URLs carry start parameters. Reloading Caddy affects every project on the host, so validate the file with `caddy validate` inside `wished-caddy` before `caddy reload`.

`deploy/deploy.sh` runs in the checkout on the host. It runs `deploy/preflight.sh`, which refuses a missing or world-readable `.env.production`, short secrets, a malformed bot token or operator list, `FEEDBACK_ENABLED=true`, demo mode, a missing proxy network, backup directory, or Caddy site block, and a dirty tree. It then builds both images tagged with the commit, dumps the database to `/var/backups/iter/pre-deploy-*.dump` (keeping the five newest), migrates, starts the stack, checks that `iter-web` resolves to exactly one container from Caddy, and waits for HTTPS. On failure after the start it restores the previous API and web images; it does not downgrade the schema. `.github/workflows/deploy.yaml` runs the same script over SSH from the `production` environment after a successful `main` CI run, and also supports manual dispatch. `deploy/production.env.example` lists the runtime settings.

The production stack was rehearsed locally on a stand-in proxy network: migrations ran on an empty database, all services became healthy, the site answered over the proxy network while the API did not, and the backup command produced a restorable dump. A real Telegram client launch, TLS, and the shared Caddy reload have not been exercised.

## Human steps before deployment can be enabled

The operator reports that the proposed host is in Helsinki, Finland. [Article 12 of Kazakhstan's personal-data law](https://old.adilet.zan.kz/eng/docs/Z1300000094) requires personal data to be stored in a database in Kazakhstan. Production stores company names, websites and business addresses, operator Telegram user IDs, and, once enabled, review and report text. Obtain qualified review of whether these are personal data under that rule before relying on this host, and keep `FEEDBACK_ENABLED` off until then. The host firewall (`ufw`) is inactive; confirm that a provider-level firewall admits only 22, 80, and 443.

`main` requires a pull-request review, a passing `verify` check, and resolved conversations, but repository admins may bypass these and push directly; a direct push still runs CI, and production deployment starts only after that revision passes. Restore admin enforcement before relying on review as a release gate. The GitHub `production` environment holds `SSH_HOST`, `SSH_USER`, `DEPLOY_PATH`, `SSH_PRIVATE_KEY` (a key used only for this deployment), and `SSH_KNOWN_HOSTS` (the pinned host key), plus the `ITER_DOMAIN` variable. Runtime secrets live only in `.env.production` on the host.
