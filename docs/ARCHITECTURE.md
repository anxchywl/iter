# Architecture and security

## Shape and ownership

The backend is FastAPI with PostgreSQL and versioned Alembic migrations. The frontend is one Next.js App Router site in `frontend/`, server-rendered for ordinary browsers and Telegram Mini App webviews. It reads the public FastAPI API from the server without caching vacancy responses. Telegram direct links pass only a listing ID through `startapp`; optional Telegram configuration never gates ordinary web browsing. Public browsing does not authenticate or create a student account.

One backend process uses PostgreSQL for employers, vacancies, reviews, reports, and audit history. Public reads enforce the 14-day confirmation cutoff directly in SQL and detail checks. A protected, bounded reconciliation endpoint persists `expired` states and audit events; correctness does not depend on calling it. An operator-only `listings-needing-confirmation` filter exposes stale confirmations without a background queue. No Redis, object storage, task queue, scraper, payment service, or second client is required.

The backend exposes operator-only HTTP endpoints without a browser admin surface or employer account. Every admin read and write requires a distinct, long bearer secret configured per operator on the server; the resolved operator ID is recorded with each audit event. Tokens are never accepted in URLs or returned to clients. Admin writes use row locks and expected versions in one transaction, so stale edits fail rather than replacing a newer confirmation. A future browser admin needs its own session and CSRF design before use.

## Data boundaries

Public endpoints may read only current published vacancies and approved reviews, plus a minimal unavailable response for previously published vacancies. They never return drafts, pending/rejected review text, reports, reporter metadata, moderation reasons, operator records, or audit metadata. Public review responses are explicit allowlists with role, season, submission date, structured answers, redacted text, and a count. Publicly citable source URLs are public listing facts; private verification material and correspondence are not stored or returned. The Next.js site forwards bounded review and report JSON to the FastAPI API through same-origin route handlers; server validation remains authoritative. Review submission writes only a pending record. Report intake writes only a private queue record. The server sets status, timestamps, and record IDs; a visitor cannot submit publication state, trust status, approval, or operator identity.

The review flow is visitor browser → Next.js feedback route → FastAPI validation → PostgreSQL pending review → operator redaction/decision → approved public read. The report flow uses the same entry path, then an operator-only queue and an audited decision. No student account, Telegram identity, contact details, upload, private messages, or raw client IP are stored with reviews or reports. The in-memory rate limiter sees the frontend server as the caller when writes are proxied; production traffic needs a trusted client-address mechanism and a shared limiter before public submissions are enabled. Do not treat browser-supplied forwarding headers as proof of client identity.

`GET /api/v1/listings` accepts `q`, `season`, `state`, `city`, `category`, `start_from`, `end_by`, `min_wage` with required `wage_currency` and `wage_basis`, `min_hours`, `housing_known`, `confirmed_within_days`, `page`, and `page_size`. The API bounds page size at 50.

A previously published detail returns HTTP 410 with only a public `stale` or `unavailable` reason. The former means the confirmation TTL elapsed; the latter covers other noncurrent states without exposing operator notes.

Write requests have a 16 KiB body limit. A single-process, in-memory rate limiter keeps a salted digest of the client IP: 100 review attempts per minute, five new review submissions per hour, and 60 other writes per minute. Expired digests are pruned on a later write, no more often than once per minute; the limiter stores no raw IP or review text and caps active keys. An exact review retry can return its existing receipt after the hourly new-submission limit. Run one backend process for this prototype; a multi-process deployment needs a shared limiter before public submissions are enabled. Configure a trusted proxy so the backend sees the real client address without trusting arbitrary forwarded headers, and keep proxy logs free of review text, Telegram init data, and outbound link parameters. Do not claim anonymous submissions prove employment.

Treat employer sources, vacancy text, review text, report text, and Telegram data as untrusted input. Review free text rejects digits, `@`, and URL-like text before storage; a moderator still checks for names or obfuscated contact details before approval. Render text without executable HTML. Accept only validated HTTPS employer/source links; review the final destination and do not create a server-side URL fetch or redirect endpoint for the MVP. Outbound navigation requires a visible user action and destination. Apply a CSP and other response headers suited to the actual dynamic site and Telegram embedding, rather than copying static-site headers. Do not trust `initDataUnsafe` for access decisions; public reads need no Telegram identity. If a future protected Telegram action uses identity, validate raw init data on the server against Telegram's current specification.

The frontend uses no Telegram SDK at present. It validates outbound URLs, reveals employer contact destinations before a second explicit click, and renders API text through React text nodes. Source and evidence links show their destination in link text or accessible labels. The site does not proxy external content or accept Telegram claims as authorization.

## Failure behavior

The server determines freshness and visibility using UTC time. Feed and detail must agree when a TTL expires between requests. Database failure shows an error rather than mock jobs or stale data presented as current. Review moderation and takedowns affect public reads immediately. Preserve audit history while keeping it inaccessible to visitors. Test unauthorized writes, unsafe links, hostile text, missing evidence, season changes, concurrent moderation, expiry, and recovery from backup.
