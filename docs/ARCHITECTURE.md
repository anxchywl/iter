# Architecture and security

## Shape and ownership

The backend is FastAPI with PostgreSQL and versioned Alembic migrations. The frontend is one Next.js App Router site in `frontend/`, server-rendered for ordinary browsers and Telegram Mini App webviews. It reads the public FastAPI API from the server without caching vacancy responses. All locales share one root layout; `src/proxy.ts` passes the path locale to it for the initial `lang` attribute, so switching language is a client navigation rather than a full reload. Routes have no `loading.tsx` fallback: a navigation keeps the current page until the next one is ready, and the tapped link shows its pending state. Telegram direct links pass only a listing ID through `startapp`; optional Telegram configuration never gates ordinary web browsing. Public browsing does not authenticate or create a student account.

One backend process uses PostgreSQL for employers, vacancies, reviews, reports, and audit history. Public reads enforce the 14-day confirmation cutoff directly in SQL and detail checks. A protected, bounded reconciliation endpoint persists `expired` states and audit events; correctness does not depend on calling it. An operator-only `listings-needing-confirmation` filter exposes stale confirmations without a background queue. No Redis, object storage, task queue, scraper, payment service, or second client is required.

The backend exposes operator-only HTTP endpoints for scripts and separate browser portal endpoints. The browser has two surfaces: `/manage` for invited provider organizations and `/admin` for iter operators. Provider access is scoped by `organization_id` in every listing query; a listing UUID alone never grants access. Providers can manage private drafts, submit them, and close their own current offers. Operators review pending submissions and retain exclusive authority over evidence and publication. Admin writes use row locks and expected versions in one transaction, so stale edits fail rather than replacing a newer decision.

Provider and operator authentication are deliberately separate. An operator creates a provider profile and FastAPI generates a random company key. PostgreSQL stores only its SHA-256 hash, an eight-character display hint, and its issue time. `/portal/login` exchanges a valid key for a different random eight-hour session token; the backend stores only that token's hash and the Next.js gateway keeps the raw token in an `HttpOnly`, `SameSite=Strict`, production-`Secure` cookie. The gateway requires the configured exact origin on session creation, logout, and all management writes, accepts only JSON bodies up to 16 KiB, and forwards the session in a private header. Every provider request reloads the session and active organization, and every listing query includes `organization_id`. Key replacement deletes all sessions for that organization. The full key is never returned again after creation or replacement, is never placed in a URL, and is not written to audit details.

Operators still use signed Telegram Mini App init data. The client sends raw init data as `Authorization: tma <init data>` and FastAPI recomputes Telegram's HMAC-SHA-256 signature, rejects duplicate fields, oversized data, an `auth_date` older than eight hours or more than a minute in the future, and accepts only IDs in `OPERATOR_TELEGRAM_IDS`. Unknown Telegram users receive no provider role. Host-local scripts retain distinct operator bearer credentials. The public directory may still run as a Telegram Mini App, but neither public browsing nor company access depends on Telegram.

Admin review, report, audit, and stale-confirmation queues return at most 100 rows per request with a `next_cursor` when more exist. Pass it as `cursor` with the same filters to continue; the cursor identifies the last returned row. This avoids losing access to older records after the first batch.

## Data boundaries

Public endpoints may read only current published vacancies and approved reviews, plus a minimal unavailable response for previously published vacancies. They never return drafts, provider correction notes, pending/rejected review text, reports, reporter metadata, moderation reasons, operator records, sessions, or audit metadata. Public review responses are explicit allowlists with role, season, submission date, structured answers, redacted text, and a count. Publicly citable source URLs are public listing facts; private verification material and correspondence are not stored or returned. The Next.js site forwards bounded review and report JSON to the FastAPI API through same-origin route handlers; server validation remains authoritative. Review submission writes only a pending record. Report intake writes only a private queue record. The server sets status, timestamps, record IDs, organization ownership, and actor identity; a visitor or provider cannot submit publication state, trust status, approval, or operator identity.

The review flow is visitor browser → Next.js feedback route → FastAPI validation → PostgreSQL pending review → operator redaction/decision → approved public read. The report flow uses the same entry path, then an operator-only queue and an audited decision. No student account, Telegram identity, contact details, upload, private messages, or raw client IP are stored with reviews or reports. Both services reject public submissions unless `FEEDBACK_ENABLED=true`; local Compose opts in for testing. The in-memory rate limiter sees the frontend server as the caller when writes are proxied; production traffic needs a trusted client-address mechanism and a shared limiter before public submissions are enabled. Do not treat browser-supplied forwarding headers as proof of client identity.

FastAPI's built-in OpenTelemetry auto-configuration is disabled, so environment variables cannot start exporting request data, error logs, or stack traces. Adding telemetry needs its own reviewed design that excludes review text, report text, and Telegram data.

Rejecting or removing a review erases its stored role and free text in the same transaction as the status change. The structured answers and content hash remain for audit and retry behavior; operator reasons must not repeat private content.

`GET /api/v1/listings` accepts `q`, `season`, `state`, `city`, `category`, `start_from`, `end_by`, `min_wage` with required `wage_currency` and `wage_basis`, `min_hours`, `housing_known`, `confirmed_within_days`, `page`, and `page_size`. The API bounds page size at 50.

A previously published detail returns HTTP 410 with only a public `stale` or `unavailable` reason. The former means the confirmation TTL elapsed; the latter covers other noncurrent states without exposing operator notes.

Write requests have a 16 KiB body limit. A single-process, in-memory rate limiter keeps salted digests rather than raw client addresses or credentials. Login, provider, operator, review, and report traffic use separate buckets, so public login failures cannot consume an authenticated management allowance. Production Caddy replaces `X-Iter-Client-IP` with the connection address, the frontend forwards it over the private network, and only the production backend is configured to trust that header. Credential-specific buckets add a second limit for authenticated writes. Review submission also has a five-new-submissions-per-hour limit. Expired digests are pruned on a later write, no more often than once per minute, and the limiter caps active keys. An exact review retry can return its existing receipt after the hourly new-submission limit. Run one backend process for this prototype; a multi-process deployment needs a shared limiter before public submissions are enabled. Keep proxy logs free of review text, Telegram init data, and outbound link parameters. Do not claim anonymous submissions prove employment.

Treat employer sources, vacancy text, review text, report text, company profile fields, access keys, and Telegram data as untrusted input. The company-key migration preserves existing `organization_members` only as a temporary compatibility path; no endpoint creates new memberships, and operators must complete migrated company profiles before issuing their keys. Review free text rejects digits, `@`, and URL-like text before storage; a moderator still checks for names or obfuscated contact details before approval. Render text without executable HTML. Accept only validated HTTPS employer/source/company links; review the final destination and do not create a server-side URL fetch or redirect endpoint for the MVP. Outbound navigation requires a visible user action and destination. Apply a CSP and other response headers suited to the actual dynamic site and Telegram embedding, rather than copying static-site headers. Do not trust `initDataUnsafe`, browser cookies, or any client-side role for access decisions; server-side credential validation and organization scoping remain authoritative.

The frontend loads no Telegram SDK. Inside a Telegram client, a small bridge posts `web_app_ready`, `web_app_expand`, `web_app_setup_swipe_behavior` (vertical swipes off), and the header and background colors so the Mini App opens at full height, matches the page, and scrolling does not drag it closed; in Telegram Web it posts only to `https://web.telegram.org` and only when launch parameters are present. A click on any `target="_blank"` HTTPS link is handed to the client with `web_app_open_tg_link` for `t.me` links or `web_app_open_link` otherwise, because the webview cannot leave the Mini App itself. Decisions that need a note use inline forms, since Telegram webviews do not reliably show `window.prompt`. Only management pages read init data, and only to send it to the server. An inline script at the top of the root layout marks the document before first paint when the native proxy, launch parameters, or a stored launch are present, so the footer and detail links that open the Mini App are hidden inside it without a flash. Start parameters `job_<uuid>`, `manage`, and `admin` route to the matching page; the browser keeps the launch fragment across that redirect. It validates outbound URLs, reveals employer contact destinations before a second explicit click, and renders API text through React text nodes. Source and evidence links show their destination in link text or accessible labels. The site does not proxy external content or accept Telegram claims as authorization.

## Failure behavior

The server determines freshness and visibility using UTC time. Feed and detail must agree when a TTL expires between requests. Database failure shows an error rather than mock jobs or stale data presented as current. Review moderation and takedowns affect public reads immediately. Preserve audit history while keeping it inaccessible to visitors. Test unauthorized writes, unsafe links, hostile text, missing evidence, season changes, concurrent moderation, expiry, and recovery from backup.
